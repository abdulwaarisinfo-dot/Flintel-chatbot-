It is everything built between the prediction and the actual trade.\n\nGiving an LLM access to an order button is relatively easy.\n\nBuilding a system that can let an AI act autonomously while keeping its authority bounded, its execution deterministic, and its behavior auditable is a much harder problem.\n\nThat is where NeoTrade is trying to solve something more fundamental.\n\n✍️ NeoTrade starts with a local-first architecture\n\nNeoTrade is a desktop trading-agent client for macOS and Windows.\n\nThe application is split into two processes:\n\nDesktop app -> Runtime sidecar\n\nThe desktop app handles the interface: dashboard, configuration, approvals, wallet and chat.\n\nThe runtime sidecar performs the actual work: market discovery, research, judgment, decision gating, signing and maintaining the decision journal.\n\nThe important detail is that this loop runs locally.\n\nAgent decisions, research, memory, market snapshots and the decision trace are stored in local SQLite. The hosted platform is not required for the execution path.\n\nThat creates a clear separation between the product interface and the execution environment.\n\n✍️ The model does not control the entire trade\n\nNeoTrade's central architectural principle is:\n\nThe model contributes judgment. Deterministic code decides consequence.\n\nThe agent can research evidence, evaluate the market, choose a direction and determine a sizing tier.\n\nBut it does not get unrestricted authority over capital.\n\nBefore an order can execute, it passes through multiple controls.\n\nThere is a global trading switch, per-agent enablement, approval mode, hard limits and a deterministic Decision Gate. The Gate can reject an order based on adversarial review, spread cost, bankroll fraction and other configured boundaries.\n\nMost importantly, these limits are enforced in code.\n\nAn LLM cannot argue its way around a limit.\n\n✍️ The system also controls when the model gets to think\n\nOne detail that is easy to overlook is the wake-gate layer.\n\nBefore spending an LLM turn, NeoTrade runs cheaper checks:\n\n- Has the price moved enough?\n- Is an existing position at risk?\n- Did an order fill?\n- Is the wallet unlocked?\n\nIf nothing relevant changed, the run can be skipped.\n\nAnd the skip itself is recorded.\n\nThis is a useful design choice because a continuously running agent should not need to invoke an expensive model every time the market remains unchanged.\n\nSo the system is not simply:\n\nMarket -> LLM -> Trade\n\nIt is closer to:\n\nEvent -> Wake Gate -> Market Screen -> Research -> Judgment -> Risk Gate -> Execution\n\nEach layer has a different responsibility.\n\n✍️ Execution is isolated from the agent\n\nThe agent never receives direct signing capability.\n\nNeoTrade uses a separate signing gateway that accepts structured order intents rather than arbitrary bytes.\n\nThe gateway is designed to:\n\n- reject unknown or expired authorization;\n- fail closed when sessions are locked or requests are malformed;\n- authorize an order exactly once;\n- record every authorization decision.\n\nOrders are then signed using EIP-712 typed data required by the venue.\n\nThis separation matters.\n\nIf the model makes a bad judgment, that should not automatically mean it has unrestricted access to the wallet.\n\nThe architecture puts a boundary between thinking and signing.\n\n✍️ Idempotency solves a very practical autonomous-agent problem\n\nAutonomous systems retry.\n\nNetworks timeout.\n\nProcesses restart.\n\nRequests can be duplicated.\n\nNeoTrade therefore makes the order path idempotent by construction.\n\nEach order gets a client order ID derived from the decision's content. If the same decision is retried, it produces the same identity rather than creating another order.\n\nA replay returns the original result.\n\nIf the same ID appears with different content, the system rejects it as a conflict.\n\nEvery terminal state also produces a receipt: submitted, blocked, rejected or failed.\n\nThat gives the execution layer a simple invariant:\n\nOne decision -> one order identity -> one authorization.\n\nFor autonomous execution, this is infrastructure rather than a cosmetic feature.\n\n✍️ Self-custody is implemented at the wallet layer\n\nNeoTrade generates a standard BIP-39 wallet locally.\n\nKeys are encrypted using scrypt + AES-256-GCM and stored locally. The passphrase is never stored or transmitted.\n\nEach agent also receives its own wallet index and therefore its own derived address and funds.\n\nThe security model goes further: the company does not hold the user's private keys, and the platform is not in the execution path.\n\nThe hosted platform receives signed trade proofs for attribution and scoring, but it does not receive keys or the ability to place orders.\n\nThat is a meaningful architectural distinction from a fully hosted trading system.\n\n✍️ Skills are treated as untrusted input\n\nAnother interesting layer is the Skill system.\n\nA strategy can be represented as text, but loading that text does not automatically grant authority.\n\nFor executable skills, NeoTrade uses quarantine and inspection, content hashing,
